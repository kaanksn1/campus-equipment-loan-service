1. Introduction and Problem Definition

A campus equipment desk needs a consistent way to assess whether a borrower can receive a new loan, set its due date and calculate the fee when equipment is returned late. Manual evaluation can confuse student and staff limits, overlook a small debt or charge an additional day on an on-time return. The proposed solution is a small Java console service with explicit inputs and testable rules.

The educational policy allows students up to three active loans and staff up to five. Approval also requires active membership and zero outstanding debt. The requested period is role-dependent, and a late return incurs a daily fee with a per-return ceiling. These rules offer Boolean combinations, numeric boundaries and invalid-input classes suitable for systematic testing.

The scope follows the supplied proposal: no GUI, database, authentication, inventory reservation or payment processing. Evaluation does not actually issue equipment or update stored borrower data. Policy values are project assumptions, not claims about a real university. Development proceeded provisionally at the student's request while instructor topic approval remained unconfirmed.

Testing within quality assurance

Testing provides repeatable evidence that implemented behaviour agrees with specified requirements. It supports quality control by exposing failures; clear requirements, reviews and reproducible builds also support the broader quality-assurance process. Verification of these rules is distinct from validation with a real equipment desk: passing the suite cannot establish that the educational policy satisfies actual campus needs. The lecture material emphasises early detection, traceable tests and the limitations of testing as a proof of correctness [6].

2. Requirements Specification

The proposal is the policy baseline [8]. The full specification is in docs/requirements.md. The following identifiers are used in the executable case records.

IDRequired behaviour
FR-01Validate borrower role, nonnegative current loan count and nonnegative integer-kurus debt.
FR-02Approve only when membership is active, debt equals zero and current loans are below the role limit.
FR-03Return all rejection reasons; an approved result has none, and a rejected result has no due date.
FR-04Accept 1–7 requested calendar days for students or 1–14 for staff, inclusive.
FR-05Require checkout date; approved due date = checkout + requested days; reject calendar overflow.
FR-06Charge zero on/before due date, otherwise 100 kurus per late day, capped at 5,000 kurus.
FR-07Require all return-related dates; due must follow checkout and return cannot precede checkout.
FR-08Keep evaluation stateless and borrower snapshots and returned reasons immutable.
FR-09Provide console demo, loan/fee commands, help, readable results and controlled input-error handling.

One TL equals 100 kurus. A debt of one kurus blocks approval; a negative amount is invalid rather than a normal rejection. Counts at or above a limit are valid data that produce a rejection. Role and membership inputs are case-insensitive in the console; membership tokens must be true or false.

The proposal's requirement to reject inconsistent return dates is made precise: due date must be strictly after checkout, and return may occur on checkout day or later. This permits early return and agrees with the minimum one-day loan period. The whole request is validated before eligibility, including when the borrower is already inactive.

Dates are explicit ISO calendar dates; weekends and leap days count. There is no grace period, holiday adjustment, renewal or fee waiver. There is no dependence on today's clock or a time zone. Java 17, JUnit 5, Maven and JaCoCo fulfil the technical approach. The assignment specifies neither a minimum test count nor a mandatory coverage percentage [7].

3. Implementation

The application separates console parsing from deterministic business services. The only production dependency is the Java runtime. Maven defines Java release 17 and pins dependency/plugin versions.

TypeResponsibility
RoleHolds the student/staff loan-count and maximum-period policy.
BorrowerAn immutable Java record; validates role, count and debt in its constructor.
LoanServiceValidates a request, calculates a candidate due date and collects every eligibility rejection.
RejectionReasonNames inactive membership, outstanding fees and reached loan limit.
LoanDecisionExposes approval, immutable reasons and an optional due date.
OverdueFeeServiceValidates dates and calculates the capped fee from late calendar days.
ConsoleAppImplements help, demo, loan/fee commands, formatting and input errors.

Key design choices

The loan service validates missing data and the role-specific period first. It then uses checkoutDate.plusDays(requestedDays), translating date-range overflow into an input error. Three independent checks collect all applicable rejection reasons instead of returning after the first. Only an approved decision exposes the calculated due date.

Money is represented as long integer kurus, avoiding fractional binary arithmetic in debt comparisons and fee totals. Fee calculation uses the calendar-day difference between due and return. Nonpositive differences cost zero; positive differences are multiplied by 100 and limited to 5,000. Even the full supported date span multiplied by 100 fits within a long.

LocalDate represents an immutable date without a time or time zone [4]. Its calendar arithmetic handles month and year transitions and leap years. Explicit dates also make tests stable across machines and days. The service has no mutable fields and does not change counts or accumulate debt.

4. Test Plan and Test Design

The highest-priority risks are approving a blocked borrower, rejecting an eligible borrower and charging the wrong fee. Tests derive expected values from the requirements, not from production helper methods. Business logic is tested directly; console parsing/output is tested as a component; the packaged executable receives separate process-level smoke checks.

Eight-rule decision table

A = active membership, Z = zero debt, C = current count below the role limit. Other inputs are valid. The complete Boolean model has eight rules. Each is executed once for each role, producing 16 cases.

RuleAZCExpected decision
1TTTApprove; due date present; no reasons
2TTFReject: loan limit
3TFTReject: outstanding debt
4TFFReject: debt and loan limit
5FTTReject: inactive membership
6FTFReject: inactive and loan limit
7FFTReject: inactive and debt
8FFFReject: all three reasons

Every rejected result must have no due date. Checking the complete reason list catches an implementation that stops after the first failure. Exhausting this small Boolean model does not exhaust all numeric and calendar inputs.

Negative testing and regression

Negative tests cover null roles/borrowers/dates, negative numbers, invalid periods, impossible dates, unsupported console tokens and numeric overflow. State tests attempt to mutate returned reasons and make unrelated successive calls. After each controlled fault experiment, the unmodified project is available for regression; after all experiments, the entire original suite is rerun and its results are preserved separately. The full design is in docs/test-plan.md.

Controlled defect detection

Three faults were deliberately injected into isolated temporary copies after the correct baseline. They are seeded experimental defects, not claims about accidental student development mistakes. Existing relevant tests were run without changing their expected results.

IDInjected defectFailing casesExpected vs actual example
FI-01Loan limit off-by-one2CAP-03: false vs true
FI-02On-time return charged as one day late4FEE-03: 0 vs 100
FI-03Per-return fee cap removed2FEE-08: 5000 vs 5100

FI-01 changes the capacity comparison from greater-than-or-equal to greater-than, incorrectly allowing an applicant exactly at the limit. Restoring the original comparison prevents that approval. FI-02 adds one to the late-day count; keeping the plain date difference restores free on-time return. FI-03 removes the cap; restoring the minimum of calculated fee and 5,000 kurus prevents overcharging.

Each faulty version ran nine relevant cases. FI-01 caused two assertion failures, FI-02 four and FI-03 two, with no test errors. After restoring each copy's correct source, all nine targeted cases passed again. Raw failure and repaired-run logs, Surefire results, exact diffs and expected/actual values are preserved under evidence/fault-injection. Source hashes confirm that original Java source and POM were unchanged by verification. The final full regression passed all 103 cases.

Interpretation and limits of coverage

The lecture's RIPR model explains the evidence: a test reaches the faulty comparison/calculation, produces an incorrect decision or fee, propagates it into the returned value and reveals it through an assertion [6]. Merely executing the same line would not necessarily reveal the fault.

JaCoCo instruction counts measure executed bytecode, line counts measure executed source lines, and branch counts cover decision outcomes; exception handling is not counted as branches [3]. These metrics cannot prove that requirements, assertions or all input combinations are correct. The three selected faults demonstrate detection of specific mistakes, not a comprehensive mutation score.

7. Discussion and Conclusion

Effectiveness of the approach

The small scope made it possible to connect every requirement to executable evidence. Decision-table tests establish all combinations of the three eligibility conditions for both roles, while boundaries target the comparisons that distinguish valid periods, available capacity, first late day and fee cap. Negative cases ensure invalid data is reported deliberately. Calendar examples check behaviours that simple integer inputs would miss.

Automated unit testing makes these checks repeatable and inexpensive to rerun after changes. A single build runs the suite and generates coverage. Independent expected examples and the fault experiments provide evidence of assertion effectiveness beyond a high coverage value. Reviewing requirements and code also supports early defect prevention, consistent with the lecture's review practices [6]. No multi-person formal review is claimed for this individual project.

Implementation and learning challenges

The actual setup exposed a Java-version mismatch: the machine defaulted to Java 8, while the proposal specified Java 17. A separate JDK and Maven Wrapper resolved the build environment. Some lecture examples use JUnit 4 imports and lifecycle annotations; the implementation instead follows the required JUnit 5 API.

The main design challenges were distinguishing a normal rejection from invalid input, returning every applicable reason, preserving integer money semantics and defining consistent date ordering. Parameterized tests reduced repetitive test code while preserving a separate, identifiable record for each concrete scenario. The source and accompanying guide explain these choices and support student review of the Java and testing concepts.

Limitations and possible improvements

The service trusts a caller-supplied borrower snapshot. Without storage or inventory integration it cannot prevent simultaneous requests from exceeding a real equipment pool, update counts or collect fees. The chosen numeric policy has not been validated with an operating campus desk. Tests do not exhaust all possible dates and integers. No performance benchmark, real stakeholder acceptance study or comprehensive mutation analysis was performed.

Future work could validate policy with stakeholders, add persistent loan records and transactional inventory control, and broaden property-based or mutation tests. These extensions are outside the submitted proposal's small console scope. Within the defined scope, the final implementation satisfies the tested rules and the original suite passes after the controlled defect experiments.
