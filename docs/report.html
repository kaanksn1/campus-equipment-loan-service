1. Introduction and Problem Definition

A campus equipment desk needs consistent borrowing decisions, due dates and late-return fees. This Java 17 console application evaluates an explicit borrower snapshot and return dates. The educational rules are project assumptions. The scope excludes GUI, database, inventory, payments and actual equipment issuance. A decision does not update a borrower's loan count.

Systematic tests check the specified behaviour; reviews, clear contracts and repeatable builds also support quality assurance. Passing tests verify the implemented rules but do not validate them as an actual university policy [1, 5].

2. Requirements Specification

IDRequired behaviour
FR-01Require STUDENT/STAFF role; reject missing role, negative loan count or negative debt.
FR-02Approve only with active membership, zero debt and count below 3 (student) or 5 (staff).
FR-03Return all applicable rejection reasons; rejected decisions have no due date.
FR-04Requested days: student 1–7, staff 1–14 inclusive; otherwise input error.
FR-05Approved due date = checkout + requested calendar days; reject date overflow.
FR-06On-time/early fee = 0; late fee = 100 kurus/day, capped at 5,000 kurus per return.
FR-07Require checkout, due and return dates; due > checkout and return >= checkout.
FR-08Stateless evaluation; immutable borrower data and returned rejection reasons.
FR-09Console demo/help and loan/fee commands; malformed input produces exit code 2.

A count at or above the limit and positive debt are valid inputs that cause normal rejection. Negative values and out-of-range periods are invalid. Validate the complete request before evaluating eligibility. One TL is 100 kurus; even one kurus of debt blocks approval. Dates include weekends and leap days; no grace period or holiday adjustment applies.

3. Implementation

Role holds policy limits; Borrower validates an immutable snapshot; LoanDecision carries the result and RejectionReason names the causes. LoanService and OverdueFeeService implement the rules, while ConsoleApp handles parsing and output. Java 17, Maven, JUnit 5 and JaCoCo are configured in the POM. Production code has no third-party runtime dependencies.

Eligibility: LoanService.requestLoan excerpt

Nulls, requested period and date overflow are validated before this block. The candidate date is calculated with checkoutDate.plusDays(requestedDays). Separate checks preserve every reason.

List<RejectionReason> reasons = new ArrayList<>();
if (!borrower.activeMembership()) {
    reasons.add(RejectionReason.INACTIVE_MEMBERSHIP);
}
if (borrower.outstandingFeeCents() > 0) {
    reasons.add(RejectionReason.OUTSTANDING_FEES);
}
if (borrower.currentLoanCount() >= borrower.role().loanLimit()) {
    reasons.add(RejectionReason.LOAN_LIMIT_REACHED);
}
return new LoanDecision(
        reasons.isEmpty() ? candidateDueDate : null, reasons);

Fee: OverdueFeeService.calculateFeeCents excerpt

Missing or inconsistent dates are rejected first. These lines then calculate lateness and apply the cap. DAILY_FEE_CENTS is 100; MAXIMUM_FEE_CENTS is 5,000.

long lateDays = ChronoUnit.DAYS.between(dueDate, returnDate);
if (lateDays <= 0) {
    return 0;
}
return Math.min(lateDays * DAILY_FEE_CENTS, MAXIMUM_FEE_CENTS);

Integer long values avoid fractional money arithmetic. LocalDate represents date-only values, handles month/year and leap-day transitions, and avoids current-clock dependence [4]. The full supported date span multiplied by 100 fits in long. Returned reasons use List.copyOf; a rejected decision exposes an empty Optional for its due date.

Source excerpts are whitespace-formatted; the complete classes remain in src/main/java. The console accepts integer kurus and ISO dates. Normal business rejection has exit code 0; invalid input has exit code 2 and an error on stderr.

4. Test Plan and Test Design

Primary risks are incorrect approval, invalid input accepted as valid, calendar mistakes and overcharging. Expected values come from requirements and literal examples. Unit tests target services; component tests target console parsing/output; separate JAR checks cover process behaviour.

TechniqueApplication and selection rationale
Equivalence partitioningDebt: negative/zero/positive; count: below/at/above limit; return: early/on-time/late. Representatives exercise distinct behaviours.
Boundary value analysisCheck neighbours of count, period, first late day and fee cap; these expose incorrect comparisons and off-by-one calculations.
Decision tableAll eight combinations of active membership, zero debt and available capacity; execute for both roles (16 cases).
Negative testingNulls, negative values, invalid periods, date ordering/overflow and malformed console tokens must be rejected deliberately.
Regression testingRerun existing tests after each controlled fault is repaired and rerun the complete original suite after all experiments.

5. Test Implementation and Results

JUnit 5 @ParameterizedTest with @CsvSource/@MethodSource expresses related examples; @Test covers distinct cases. Fresh fixtures and explicit dates make tests repeatable [1]. CaseEvidence records inputs, expected/actual values and requirement IDs, then calls assertEquals. JUnit also checks complete reason lists, absent due dates, immutability and exception behaviour.

Controlled faults and real unsuccessful executions

Each fault was deliberately seeded in a temporary copy. Existing expected values were unchanged; these are controlled experiments, not claims about accidental student mistakes.

FI-01 uses > instead of >=, admitting a borrower at the limit. FI-02 adds one late day, charging an on-time return. FI-03 removes the 5,000-kurus cap. The experiments produced 2, 4 and 2 genuine assertion failures, respectively, with no test errors. After restoring each copy, all nine targeted tests passed. The complete original suite also passed all 103 cases after the experiments.

Exact diffs, failing and repaired results, and logs are preserved under evidence/fault-injection. Source checksums verify that the original Java files and POM were unchanged by the experiments.

What coverage does and does not establish

Execution coverage cannot prove correct requirements or assertions. A test must reach a fault, produce an incorrect state, propagate it to an observable result and reveal it with a check (RIPR) [5]. The boundary tests reveal these selected faults; three experiments do not constitute comprehensive mutation testing. High coverage therefore supports, rather than replaces, meaningful expected results.

7. Discussion and Conclusion

Decision tables cover combined eligibility conditions; boundaries expose comparison and fee-cap mistakes; invalid-input tests enforce contracts; regression checks expose unintended changes. JUnit makes these checks repeatable after edits and gives each concrete case an identifiable result [1]. The controlled failures show that assertions detect selected faults beyond merely executing code.

Implementation challenges included selecting Java 17 when the original machine used Java 8, distinguishing invalid input from normal rejection, and consistent date/money semantics. Explicit dates, integer kurus and a Maven Wrapper made the build and tests repeatable. Parameterized tests reduced duplication while keeping separate records for each example.

Personal contribution and reflection

I selected the equipment-loan topic and small console scope, provided the proposal and emailed the instructor to request approval. In the examples, I identified that a borrower already at the loan limit must be rejected, while a negative debt value is invalid input. I checked that three late days cost 300 kurus and that a longer delay cannot raise the fee above 50 TL. I ran the full build and all 103 tests passed, then compared the demo and two console scenarios with their expected outputs. These runs confirmed the rejection at three student loans and the 300-kurus fee for a three-day delay; their terminal logs are preserved. ChatGPT explanations helped me study Java, JUnit, test design and the difference between an expected result and the program's actual output.

The service trusts supplied snapshots and has no persistence or concurrent inventory control. The policy has not been validated with an operating equipment desk; tests do not exhaust every date or integer. Within scope, broader fault selection and additional calendar combinations could improve the evidence. The tested rules pass the suite, with limits stated above.
